# Backlog

Design notes and known quirks to come back to. Each entry says what happens now, where, and why it was left. Rules that already differ from the original server are in [deviations.md](deviations.md); move an entry there once it is decided and built.

## Design ideas

- **Valley upgrades and flat land.** `upgradeValley` (`backend/packages/game/src/services/combat.ts`) accepts flat land, because `VALLEY_TYPES` includes `TileType.FLAT`, and the client offers it. Flat land can never be attacked or held, so the upgrade only raises the tile's level. That level stays with the tile: settling or teleporting a city onto it keeps it under the city, and teleporting away leaves a flat of that same level behind (`interior.moveCity` only changes the tile's type). Generated flats are levels 1–10, low levels more common. Kept for now; there are ideas for what upgraded flats could mean.
- **Scripted play (bots).** Nothing tells a player from a script: the API answers any client with a valid token, and anything the browser sends a script can send too (the same headers, `Origin` and token, or a headless browser), so the API can't be limited to the game's own client. The original Evony was full of bots: farming barbarian camps round the clock, building and training queued by script, armies timed to the second. Rate limits don't help (a bot can stay under any limit a busy player needs), and the login backoff and the sign-up puzzle (`backend/services/api/src/auth/`) only guard the door. Left for now because it's a design question more than a security one:
  - *Make scripting pay less:* the game's own automation (flows, farm lists) already does much of what bots did, so a player gains little from a script.
  - *Detect it:* patterns no person keeps up (actions at all hours without a break, reaction times of milliseconds), shown to the server operator to look at, never acted on automatically.
  - *Decide the rules:* what's allowed (a player's own helper scripts?) and what happens to a player caught breaking them.
- **More for the 3D hero.** The 3D figure ([features/hero-3d.md](features/hero-3d.md)) shows only on the Heroes page's character sheet, and its gear icons don't point at it. Two ideas from its design, left as nice-to-haves once the figure was done:
  - *A piece lit when its icon is hovered:* the meshes are already named after their pieces (`buildFigure`, `paper-doll/hero-figure-3d/utils.ts`), so hovering an icon in `PaperDoll` could tint those meshes (a uniform in the toon material, as the glow is).
  - *The 3D hero elsewhere:* the Inn's offers, or the famous heroes once they exist (TODO.md). Each would load three.js too, so it suits a screen that shows one hero at a time.

## Known quirks

- **An unreachable refusal in `trainSplit`.** `training.trainSplit` refuses a fortification with `training.fortsAtWalls`, but `assertCanTrain(…, fort = false)` refuses it first with the vaguer `common.invalidTroopType` (`backend/packages/game/src/services/training.ts`). The request is refused either way; only the message is less specific. Fix: check for a fortification before `assertCanTrain`, or drop the second check.
- **`readReport` returns the read flag from before it was opened.** It reports `isRead: false` the first time a report is opened (and marks it read), while `mail.readMail` returns `isRead: true` (`backend/packages/game/src/services/reports.ts`). The client does not use the flag from this response.
- **Alliance member counts can be stale.** `alliances.memberCount` is only refreshed by `refreshAllianceStats` (the rankings job, `backend/packages/game/src/engine/alliance.ts`), so `allianceInfo`, `listAlliances` and `myInvites` show the count from the last refresh, while `myAlliance` counts live (`backend/packages/game/src/services/alliance.ts`). Accepted for now.
- **Rescheduling a timed event keeps its old player and city.** `flush` (`backend/packages/game/src/context.ts`) upserts a timed event by its ref key, updating its time, payload and type but not `player_id` / `city_id`. No caller reuses a key for another player or city today.
- **A failed stats write loses fractions.** When `flushStats` (`backend/packages/game/src/stats.ts`) fails it puts the counters back for the next try, but already rounded.
- **An empty `?techId=` reads as tech 0.** The research speed-up cost route coerces an empty query value to 0 and answers `research.notResearching` for it, instead of refusing the request.
- **The 3D hero's frame time on a tablet is unmeasured.** A frame takes about 0.5 ms to draw on an M5 Pro (Chrome), it redraws about 12 times a second at rest and at the screen's rate while dragged or acting ([features/hero-3d.md](features/hero-3d.md), phases 1 and 4), but no tablet or phone was to hand to measure. Reduced motion (it stands still, doesn't act and stays where it's turned) was likewise only checked in code and tests, as the test browser can't ask for it. To do on a device: drag the figure and tap through the actions, with and without reduced motion.
- **A woman's braid hides behind her near pauldron in 3D.** The braid runs from behind the ear over the near shoulder (`buildFigure`, the hair section), and at rest the pauldron and the sword arm cover most of it, so only a strip down the neck shows; the 2D figure shows it down the chest. Moving its end further in front and towards the middle would show it. Left as a look to tune, not a fault.
- **The 3D swing is the least clear action.** It strikes forward and down (`ACTION_KEYS.swing`, `paper-doll/hero-figure-3d/constants.ts`), which the three-quarter view foreshortens, so it reads less than the salute and the shield. Adding a turn about z (a sweep across the body) would show more; only numbers to change. Left as a look to tune.
- **English text in the first page.** en-GB is the fallback locale, so its text for every screen is bundled into the first page's `app` chunk (`src/lib/i18n.ts`), along with `BALANCE`, even for screens that load later (the Market, the Factions panel, reports). Every feature with new text grows the chunk: faction standing pushed it past its 115 kB budget, which was raised to 118 kB (2026-10-31, `client/web/.size-limit.js`). A fix: bundle only the namespaces the first page shows (common, game, the town's) and load the rest of en-GB with the screens that use them, as other locales already load (`src/locales/ja-JP.ts`). Left because it touches every lazy screen's first render (text must be there before it draws).

## Operations

- **Error tracking (alerts and grouping) instead of reading logs.** Today errors only reach the container logs, and production stack traces are decoded by hand with the image's trace tool ([deployment.md, Reading a stack trace](deployment.md#reading-a-stack-trace)). The bundles are fully minified and their source maps ship in the image unused, because Node's `--enable-source-maps` costs about 45 MB per process (measured on the API: 85 MB → 130 MB at steady state). An error tracker would email on new errors, group repeats and show source-mapped traces itself (maps uploaded per release at build time, e.g. with `sentry-cli`). It does not save memory: it adds an SDK to the API and the worker (to measure; likely 10–40 MB each with performance tracing off) and, if self-hosted, the tracker itself. Options weighed in October 2026:
  - *Sentry self-hosted*: about 16 GB of RAM and around 40 containers; far too heavy for one game server.
  - *GlitchTip*: MIT, uses the Sentry SDKs, about 256–512 MB (web, worker, Postgres, optionally Redis/Valkey), source maps uploaded per release with `sentry-cli` or its own CLI (reportedly not the newer debug-ID uploads), needs a persistent volume for them, also does uptime checks. The best open-source fit: its own database in the existing Postgres, on a machine with 4 GB or more.
  - *Bugsink*: one container on SQLite, Sentry-SDK compatible, lists source-map support; source-available under Polyform Shield (free for your own use, not OSI open source).
  - *A hosted service* (Sentry's free tier, small monthly quota): no RAM on the machine and no upkeep, and it still alerts when the machine itself is down; the data leaves the machine.
  - Whichever is chosen, add an external uptime check too: a tracker on the same machine can't report that machine going down.
  - Sources: [Sentry self-hosted requirements](https://shop.zimaspace.com/pages/sentry-self-hosted-hardware-requirements), [SSD Nodes on Sentry alternatives](https://www.ssdnodes.com/learn/lang/de/self-hosted-error-tracking-sentry-alternatives), [GlitchTip CLI](https://glitchtip.com/documentation/cli), [GlitchTip source maps with sentry-cli](https://glitchtip.com/blog/2022-04-25-glitchtip-1-12), [GlitchTip source maps need a volume](https://railway.com/deploy/sentry-compatible-error-tracking-glitchtip-v623-source-maps-survive-redeploys--sentry-compatible-error-tracking-or-glit), [Bugsink overview](https://noted.lol/bugsink/), [Bugsink licence](https://openapps.pro/apps/bugsink).
- **Client download size: what's left to try.** Measured October 2026 after compression, removing zod from the client and splitting it into files (AGENTS.md, Client rule 7; a size budget, `client/web/.size-limit.js`, now fails the build if it grows): the first page is about 271 kB over the wire (was 2,094 kB), and the game tabs and Japanese are fetched separately. Further options, roughly by value:
  - *Brotli* instead of gzip: another 15–20% smaller. The official nginx image has no brotli module; either build nginx with `ngx_brotli`, or serve the client with Caddy (`file_server` with `precompressed br gzip`, and `encode` for API responses), with `tools/build/precompress.mjs` also writing `.br` files.
  - *HTTP/2 or HTTP/3*: plain nginx serves HTTP/1.1; the HTTPS setup (Caddy, deployment.md) already gives HTTP/2 and HTTP/3, where the extra files of the split cost almost nothing.
  - *WebSocket compression* (permessage-deflate in `@fastify/websocket`'s `ws` options, `perMessageDeflate`): pushes are small JSON, so measure first; it costs server memory per connection.
  - *A service worker* caching the hashed files: instant repeat visits and some offline tolerance, at the cost of update handling (a new deploy must replace the cached app).
  - *Rendering on slow phones*: the Map tab renders about 250 buttons and Items about 95; virtualising long lists would help low-end devices if they feel slow.
  - *WebAssembly: considered, not worth it.* The client is a DOM interface fed by the API; its time goes to the network and rendering, not computation, and WebAssembly can't touch the DOM (it calls through JavaScript). Rust UI frameworks ship larger first downloads, and a rewrite would drop React, Radix and i18next. WebAssembly only pays for heavy computation in the browser (a client-side battle preview, if the TypeScript simulator ever proves too slow there), as one module, not the app.
