# Browser tests with Playwright

**Status:** built 2026-11-09, every phase: the core flows, phones, right to left, the dark theme and axe on every screen and its tabs, with nothing allowed (123 tests in four projects, about a minute with 9 workers locally); a CI workflow (`browser.yml`, phase 5) GitHub runs on every push to `main` and every pull request; Firefox and WebKit on request. TODO.md item: *Browser tests with Playwright* (Code quality and security).

**The aim:** the real game, played in a headless Chromium against the running stack, checks what no other test reaches: the built bundle as nginx serves it, routing and the address, the screens loaded on first use, the sign-up puzzle's Web Worker, accessibility, phones and right-to-left layout. A small suite of the flows that matter, not a test of every rule: the game's rules stay covered by the service tests.

## Where things stand

- **The client's tests are pure functions in plain Node** (`client/web/src/**/*.test.ts`, no DOM, no JSX; AGENTS.md, Client, Tests). Nothing renders a component or opens a page.
- **The end-to-end checks are scripts against the API** (`tools/smoke/*.mjs`: `smoke`, `war`, `market`, `abandon`, `pvp-off`, and the load test `load.mjs`). They make `fx_…` accounts, solve the sign-up puzzle in Node (`tools/smoke/proof.mjs`) and send requests as the client would, but never load the client.
- **Accessibility is linted, not tested:** `jsx-a11y-x` checks the JSX, but nothing checks the rendered page (contrast, names of controls built from data, focus order, a dialog's labelling).
- **CI** (`.github/workflows/ci.yml`) runs typecheck, lint, format, the unit tests, both builds and the service tests on every push to `main` and every pull request; `npm run ci:local` runs the same with act.

## Decided

- **Headless Playwright** (2026-11-09, the maintainer's choice), Chromium only to start.
- **Against the running Compose stack** (2026-11-09): the web container's nginx, so the tests load the bundle players get, not the Vite dev server. `WEB` if set, else `http://localhost:<WEB_PORT>` from the repo's `.env` (`e2e/support/stack.ts`): the main dev stack by default, and a worktree's second stack (README.md, A second stack for a worktree) from its own checkout.
- **A CI workflow of its own** (2026-11-09, phase 5): `.github/workflows/browser.yml`, beside CI's (`ci.yml`), and locally with act (`npm run ci:browser`). First run by hand only; the same day the maintainer had GitHub run it on every push to `main` and every pull request, as CI is: the private repository's minutes cover it (CI's two jobs take about 6 minutes each on GitHub's runners, this one an estimated 6–8, at $0.006 a minute past the plan's allowance), and public repositories run free. `npm run ci:local` now runs `ci.yml` alone (`-W`), so the usual checks don't get slower. How it runs:
  - in the `node:24-bookworm` image like CI, Playwright installing its browser and the system libraries it needs (`--with-deps`), with Postgres as a service; it builds both bundles, migrates, starts the API and the worker from the bundles (`NODE_ENV=production`, as the backend image sets: without it the API logs through pino-pretty's thread, which a bundle can't start) and serves the built client with `vite preview`, which proxies `/api` as the dev server does; the worker seeds the world in about a second;
  - starting the stack and running the tests in one step: under act each step is a process of its own, and servers started in the background end with their step;
  - on `127.0.0.1`, not `localhost`: `vite preview` listens on one of IPv4 and IPv6, and Node's `fetch` tried the other;
  - `GAME_SPEED=60`, so the battle report test runs; with Chromium only about 2½ minutes (installing the browser 25 s, the tests about a minute), and the logs of the API, the worker and the client printed if it fails;
  - an input, `browsers`: `all` adds Firefox and WebKit (`npm run ci:browser -- --input browsers=all`).
- **The dark theme is a project** (2026-11-09): `dark` runs the desktop specs with the system in dark mode, which the game follows (next-themes, `main.tsx`), so every flow and axe check runs in both themes. It found nothing the light theme didn't.
- **Axe beyond a new account's first look** (2026-11-09, `content.spec.ts`, desktop and dark): every tab of every page and panel (clicked one by one: a tab can open more), a hired hero's character sheet in 3D and 2D, a building's details, City settings and Player settings, a new flow and the Plans panel's new-plan form, the market after a trade, the map with the city's own tile selected, and a battle report. The report needs an army to land, so it's the one test that waits for game time and skips itself below `GAME_SPEED=30` (read from `GET /player`).
- **A killed run's accounts are cleaned up by the next run** (2026-11-09): each run's list of accounts (in the system's temp folder) is named after the checkout, and the global setup deletes the accounts in any list of this checkout untouched for 30 minutes, then the list (`staleAccountFiles`, `e2e/support/cleanup.ts`). A run in progress is never touched (a whole run takes about a minute), nor another worktree's. Checked by killing a run with SIGKILL after its first account was made: the next run's setup deleted it.
- **Firefox and WebKit on request** (2026-11-09): `E2E_BROWSERS=all npm run e2e` adds them (the desktop specs; `npx playwright install firefox webkit` once, about 200 MB). WebKit passes every test, on this Mac and on Linux. Firefox passes every test on Linux (the CI image), but Playwright 1.64.1's Firefox 157 doesn't start on macOS 27 ("Could not find profile folder", even launched by hand with a profile folder that exists): try again with Playwright 1.65 (out 2026-11-05, old enough from 2026-11-19). Two things only Firefox showed, neither a fault in the game: without a GPU it has no WebGL, so the hero falls back to the 2D figure by design (the test checks 3D only where WebGL 2 is there); and it logs a font download it cancelled when the page changes as an error (`NS_BINDING_ABORTED`, status 2152398850), which the error fixture skips (a missing font still fails).
- **No visual snapshots** (2026-11-09): every screen shows the player's own coordinates, names, timers, prices and a random place on the map, so a full-page snapshot needs so much masked that little is left to compare; fonts render differently on a Mac and in the Linux image, so baselines would be per machine; and the sprites are already checked by `lib/game-art.test.ts` (every file there) and drawn by code (`npm run art:draw`). Screenshots compared for one change, as the tabs fix was (phase 4), do the job when a change should look the same.
- **Temporary `fx_e2e_…` accounts, deleted afterwards** (2026-11-09), as AGENTS.md, Running stack asks: never an account the tests didn't make. The maintainer plays on the dev stack, so the tests leave the shared world as they found it where they can: the army is recalled before it lands, the market order cancelled. What happens in the test's own city doesn't matter, as the city goes with the account.
- **Set-up through the API, finished with the game's own speed-ups** (2026-11-09, `e2e/support/city.ts`): a new city has only a Town Hall, and a test that trains, sends an army or trades needs buildings first. They're built in slots 26–31 (so the building test's first free slot never meets them) and finished at once: the free speed-up covers anything with 5 game minutes or less left, which is every level 1 or 2 the set-up needs but the Marketplace (12½ game minutes), finished with gold (40,000 of the city's 100,000). A building waits for the city's construction to be free first. Troops can't be bought done (Otto's Muster Roll is 250,000 gold), so one militia is trained for real: 25 game seconds, the one wait, 0.4 s at the dev stack's `GAME_SPEED=60`.
- **An attacking army needs a hero** (`army.heroRequiredAttack`), so the army test hires one: a level 2 Cottage, an Inn and a Feasting Hall, then the Inn's first offer.
- **Phones and Arabic are projects of their own, with specs of their own** (2026-11-09): `mobile` runs `phone.spec.ts` and `languages` (first called `rtl`) runs `rtl.spec.ts` and `languages.spec.ts`; `desktop` and `dark` run everything else. The core flows aren't repeated on a phone or in Arabic: what differs there is the layout (cards, the tab bar, the menu sheet, mirroring, width), and that's what those specs check, on every screen.
- **"Wider than the screen" means the page's own scroll areas** (2026-11-09, `sidewaysScroll` in `e2e/support/screens.ts`): the document, `main` (which scrolls by itself, so overflow there never reaches the document) and an open panel. A part of a screen made to scroll sideways is allowed (the Items panel's tabs, 500 px in 342 on a phone, scroll with their scrollbar hidden). Checked it catches one: a 2,000 px element in `main` fails it.
- **Axe waits for the page to stop moving** (2026-11-09): colours are measured as drawn, and reduced motion doesn't stop CSS transitions, so a check straight after a click measured a button mid-way through its colour change or a dialog mid-fade, and failed on contrast that isn't there. `expectAccessible` waits until no finite animation or transition is running (endless ones, a loading pulse, are left out).
- **Known problems are listed, and the list can only shrink** (2026-11-09, `KNOWN` in `e2e/support/axe.ts`): an axe rule and the screens it's allowed on (`expectAccessible(page, where)`). Anything else serious or critical fails, and so does a listed problem that's no longer there, so the list is kept true as problems are fixed.
- **4xx answers are play, 5xx are faults** (2026-11-09): the browser logs every 4xx as a console error ("Failed to load resource"), and some are how the client works (`GET /player` answers 404 until the player exists, which sends a new account to the create-city page). The error fixture skips those lines and judges answers by status: a 5xx fails the test.
- **Dependencies** (versions checked 2026-11-08, pinned exactly, at least two weeks old), dev dependencies of `@marchlands/web`: `@playwright/test` 1.64.1 (2026-10-14, Apache-2.0; 1.65.0 came out 2026-11-05, too new) and `@axe-core/playwright` 4.14.0 (2026-10-15, MPL-2.0). The browser is fetched by `npx playwright install chromium` (the headless shell, about 100 MB, into Playwright's cache outside the repo).
- **`playwright-core` 1.64.1 is a direct dependency too** (2026-11-09): axe takes it as a peer (`>= 1.0.0`), and npm installed the newest, 1.65.0, beside Playwright's own 1.64.1. The two copies' `Page` types didn't match, and 1.65.0 is too new anyway. npm's `overrides` doesn't reach a peer it installs by itself, so the client lists it, pinned to Playwright's version, and npm keeps one copy. Update the three together.

## Shape

- **Files:** everything in `client/web/e2e/`: the specs (`*.spec.ts`), `playwright.config.ts`, the global setup and teardown, helpers in `support/`, and a `tsconfig.json` of its own.
  - `.spec.ts`, outside `src/`, so vitest never picks them up (it runs `client/web/src/**/*.test.ts`).
  - **Its own tsconfig** (2026-11-09; `npm run typecheck` runs it): in the client's, the web image's build (`tsc -p .` in the Dockerfile) typechecked the tests too, and failed on them. `.dockerignore` leaves `client/web/e2e` out of the images.
  - In `TYPED` (`eslint.config.js`), so the type-aware rules and import order apply; like the unit tests, they may compare raw strings (no `no-string-compare`), and React's hook rules are off (a fixture's `use` isn't React's). ESLint ignores Playwright's report and results folders. Relative imports (`./support/…`): `@/` is the client's `src`, which the tests never import.
  - knip finds the config through its Playwright plugin (`knip.json`, `client/web`) and the global setup and teardown as entries.
  - `forbidOnly` in the config fails a run with a `test.only` left in.
- **Commands:** `npm run e2e` (headless, every project; the root runs the client's `e2e` script, `playwright test -c e2e`), `npm run e2e -- --headed` or `--debug` to watch one, `--project mobile` for one project. A row in AGENTS.md, Commands, and a Browser tests section under Client.
- **Accounts:**
  - The global setup checks the stack answers and names the run (`E2E_RUN`, five random hex digits).
  - Each worker signs up one `fx_e2e_<run>_<n>` account through the API (a worker-scoped fixture, `account`): the puzzle solved with Node's PBKDF2 as `tools/smoke/proof.mjs` does (in TypeScript here, so it's typed), a player and a city, a random password, and its name added to a file in the system's temp folder.
  - The global teardown deletes every account in that file with `npm run delete-player -- … --yes`, also after a failed run; a run killed before then is cleaned up by the next one (Decided).
  - `loggedIn` is the page logged in as that account: its token put in `localStorage` (`marchlands.token`, `lib/api.ts`) before the client loads, and the town open. The login test still logs in through the form.
  - The sign-up test signs up through the form itself (`fx_e2e_<run>_s<n>`, noted for the teardown before it's made), so the puzzle's worker (`useSignUpProof`) is covered too.
  - A worker's tests share its account and city, one after another: each test gets the buildings it needs from `ensureBuilding`, which builds only what's missing.
- **Finding things:** by role and accessible name (`getByRole('button', { name })`), as a player with a screen reader would, never by CSS class or `data-testid`; a control a test can't name is an accessibility gap to fix in the client. The English text comes from the en-GB locale files (a small `text('login:form.logIn')` helper), so rewording a string doesn't break a test.
  - **The Scene's buildings** are buttons for the keyboard under the canvas (`opacity-0`, `pointer-events-none`), so a test reaches them as a keyboard user does: `press('Enter')`, not `click()`.
  - **A place on the map** is opened from the address (`map?at=x,y`), which selects its tile and shows its card, rather than by clicking the canvas.
  - The one check by CSS is the screens test's loading placeholder (`[data-slot="skeleton"]`), which has no role.
- **Stable by design:**
  - Reduced motion is on in every project (`reducedMotion: 'reduce'`), so the scenes and figures stand still (`useMotion`).
  - No test waits for game time, so the suite passes at `GAME_SPEED=1`: it checks what happens at once (a queue entry, resources spent, an army on its way, an order in the book).
  - No pixel snapshots to start with: fonts and canvas art make them flaky for little gain.
- **Every test also fails on** a console error, an uncaught page error, or a 5xx answer from the API (an automatic fixture), a cheap net under every flow.
- **On failure:** a trace, a screenshot and the HTML report (`trace: 'retain-on-failure'`), in `playwright-report/` and `test-results/`, both gitignored. No retries: a flaky test is fixed, not retried.
- **Projects:** `desktop` (1280×800, Chromium) from phase 1; `mobile` (a Pixel 7 at 375×812: touch, Android's user agent) and `languages` (desktop with the browser's language Arabic, which picks `ar`; `languages.spec.ts` sets Spanish and Japanese itself) from phase 3; `dark` (desktop in the dark theme); `firefox` and `webkit` (the desktop specs) only with `E2E_BROWSERS=all`.
- **Shared screen helpers** (`e2e/support/screens.ts`): the lists of views, pages and panels (from `lib/nav.ts`), `openScreen` (straight to a screen by its address, waiting for it: the panel itself, as a panel hides the top bar from the accessibility tree, or the city in the top bar, then nothing loading), `loading` and `sidewaysScroll`. `text()` takes a locale (`text('game:viewSwitch', {}, 'ar')`).
